# 트러블슈팅 기록 (STAR)

개발하면서 만난 문제와 해결 과정을 **S(상황) · T(과제) · A(행동) · R(결과)** 순서로 남긴다. 발표 질의응답("개발하면서 어떤 문제를 겪었나요?")과 회고에 그대로 쓴다.

**쓰는 규칙**
- 문제를 해결한 **같은 커밋**에 항목을 추가한다. 번호는 이어서 붙인다(TS-NN).
- 결과(R)에는 확인한 방법(테스트, 실행 결과)과 수치를 적는다. 확인하지 못한 것은 "미확인"이라고 쓴다.
- 분류: **기획**(설계 단계에서 잡은 결함) / **구현**(코드·테스트에서 발견) / **환경**(도구·배포·연결) / **프로세스**(작업 방식)

## 기획

### TS-01. 마지막 한 몫에 동시 신청이 몰리면 몫보다 많이 신청될 수 있음

- **S**: 서비스의 핵심 흐름은 "몫이 차면 성사"다. "남은 몫을 세고 → 신청 기록을 넣는" 방식은 두 요청이 동시에 "1자리 남음"을 읽으면 둘 다 성공해 몫보다 많이 신청받는다. 휴대폰 두 대로 눌러서는 이 상황이 재현되지도 않는다.
- **T**: 남은 몫 수만큼만 성공시키고, 마지막 몫이 차면 같은 순간에 성사로 바꾼다. 발표에서 10분 안에 설명하고 직접 시연할 수 있어야 한다.
- **A**: `filled_slots` 컬럼을 두고 몫 증가와 성사 전환을 **조건부 UPDATE 한 문장**으로 처리하기로 했다(`WHERE status='OPEN' AND deadline>now() AND filled_slots<total_slots AND owner_id<>:user`). 같은 행을 고치는 요청은 PostgreSQL이 줄 세우고, 뒤 요청은 바뀐 값으로 조건을 다시 검사하므로 행 잠금이 필요 없다. 중복 신청은 `UNIQUE(item_id, user_id)`, 초과는 `CHECK(filled_slots<=total_slots)`로 DB가 한 번 더 막는다. 시연은 동시 요청 10건을 보내는 스크립트로 한다.
- **R**: A-05로 구현했고(`app/join.py`, SQL은 기획서와 글자 그대로 같다) 동시성 테스트로 검증했다. 장벽(Barrier)으로 요청을 같은 순간에 출발시켜 5회씩 반복했다.
  - 마지막 1몫에 8명 → **정확히 1건 201**, 7건 `SLOTS_FULL`, 글은 `CONFIRMED`
  - 3몫에 8명 → **정확히 3건 201**, 5건 `SLOTS_FULL`
  - 모든 경우에 `filled_slots` = 신청 기록 수, 5xx 없음 (통과)
  - **방어가 실제로 필요한지 확인**: 같은 코드를 "남은 몫을 SELECT로 읽고 나서 UPDATE"하는 방식으로 일부러 바꿨더니 동시성 테스트 26개 중 **20개가 실패**했다(원복 후 모두 통과).
  - 아직 확인하지 못한 것: 실제 HTTP 서버(uvicorn)에 대한 부하 시연. 이 테스트는 서버 프로세스 안에서 요청을 보내므로, 발표용 스크립트(3단계)로 따로 확인한다. **일부 미확인**.
- **관련**: 기획서 5.5, 9.5, 12장

### TS-02. 같은 계정의 동시 신청에서 약속과 다른 에러 코드가 나옴

- **S**: 같은 계정이 마지막 한 몫에 동시에 두 번 신청하면, 첫 요청이 글을 성사시킨 뒤 두 번째 요청의 UPDATE는 0행이 되어 `SLOTS_FULL`로 분류된다. 문서는 `ALREADY_JOINED`를 약속했다.
- **T**: 동시 요청 상황에서도 문서가 약속한 응답과 실제 응답이 일치하게 한다.
- **A**: UPDATE가 0행일 때 원인을 가리는 순서를 고정했다: 글 없음 → **이미 신청함** → 내 글 → 마감·무산·취소 → 몫 소진. 판정용 SELECT는 새 문장이라 READ COMMITTED에서 먼저 커밋된 신청 기록이 보이므로, 동시 요청에서도 순서가 안정적이다.
- **R**: 구현하고 동시성 테스트로 검증했다(각 5회 반복, 통과).
  - 같은 계정이 마지막 1몫에 동시에 2건 → 1건 201, 1건 **`ALREADY_JOINED`**(`SLOTS_FULL`이 아님)
  - 몫이 남았을 때 같은 계정이 동시에 3건 → 1건 201, 2건 `ALREADY_JOINED`, **`filled_slots`는 정확히 1**(늦은 쪽의 UNIQUE 위반이 UPDATE의 증가까지 롤백)
  - 두 사람이 각각 2번씩 동시에 → 이긴 사람의 중복은 `ALREADY_JOINED`, 진 사람은 둘 다 `SLOTS_FULL`
  - 판정 순서를 일부러 "몫 소진 먼저"로 바꾸면 11개가 실패하는 것도 확인했다.
- **관련**: 기획서 9.5, 커밋 0e10afa

### TS-03. 무산 기록 주체와 트랜잭션 충돌

- **S**: 스케줄러를 두지 않기로 해서 무산(FAILED)을 기록하는 곳이 없었다. 모든 API가 처음에 무산 기록 UPDATE를 실행하기로 했는데, SQLAlchemy는 첫 문장에서 트랜잭션을 자동 시작(autobegin)하므로 뒤의 `begin()`이 오류를 낸다. 또 여러 행을 바꾸는 문장을 동시 신청 10건이 각자 실행하면 서로 기다리다 교착이 날 수 있다.
- **T**: 동시 신청 경로를 단순하게 지키면서 무산 상태가 화면에 정확히 보이게 한다.
- **A**: 신청 가능 여부는 항상 `deadline > now()`로 판단하게 해 정확성을 시각에 맡겼다. 무산 기록은 상태가 화면에 보이는 **내 참여(A-06), 내 글(A-08)에서만** 실행하되, 본 처리와 **별도의 짧은 트랜잭션**으로, `FOR UPDATE SKIP LOCKED`를 붙여 실행하고, 실패해도 요청은 계속한다. 응답의 상태는 저장값이 OPEN이어도 마감이 지났으면 FAILED로 내보낸다.
- **R**: 동시 신청 경로가 "조건부 UPDATE 한 문장"만 남아 교착 가능성이 없어졌고 발표 설명도 단순해졌다. 표시 상태 계산(`display_status`)은 구현했고 A-04 응답의 `OPEN` 표시만 테스트로 확인했다. 신청 경로(A-05)가 마감 지난 글을 건드리지 않는 것(저장값이 `OPEN`으로 남음)과, 동시 신청 테스트에서 5xx(교착 등)가 한 번도 나지 않은 것은 확인했다. 무산 기록 문장 자체는 A-06·A-08 단계에서 테스트한다. **일부 미확인**.
- **관련**: 기획서 5.4, 커밋 0e10afa, `backend/app/items.py`

### TS-04. 나눔 마감이 마지막 1분을 막음

- **S**: 나눔의 유통기한 날짜를 그날 23:59:00으로 저장하면 `deadline > now()` 검사 때문에 그날 23시 59분부터 신청이 막혀, "하루 전체"가 열려 있지 않았다.
- **T**: 유통기한 날의 마지막 순간까지 신청 가능하게 하고, 사용자가 날짜를 하루 늦게 읽지 않게 한다.
- **A**: 마감을 **다음 날 00:00 KST**로 저장하고 그 시각부터 불가로 정했다(끝 시각을 포함하지 않는 표준 방식). 화면에는 저장값 대신 "10/13까지"처럼 유통기한 날짜를 표시한다.
- **R**: 기획서 2·5.3·7장·QA에 반영했고 경계 시각 테스트 항목을 추가했다(23:59:30에는 신청, 00:00부터 410). 구현은 나눔 묶음 단계. **미확인**.
- **관련**: 기획서 5.3, 커밋 0e10afa

### TS-05. 몫당 가격 합계가 총액과 맞지 않음

- **S**: 몫당 가격을 올림하면 10,000원 ÷ 3몫 = 3,334원이라 합계가 10,002원이 된다. 남는 금액을 일부 참여자에게 나누면 신청 순서에 따라 누가 더 내는지가 정해지고, 신청 기록에 가격 컬럼이 필요하다. 개설자가 몫을 갖지 않는 구조라 남는 금액을 낼 사람도 없었다.
- **T**: 합계가 총액과 정확히 맞고, 참여자 가격이 모두 같고, DB를 바꾸지 않는 규칙을 찾는다.
- **A**: **개설자도 몫 1개를 갖게** 하고, 참여자는 10원 단위로 내린 같은 금액을, 개설자가 나머지를 부담하게 했다(`P = 10×⌊총액÷(10×n)⌋`). 단위는 비교해서 10원으로 정했다(100원 단위면 21명일 때 개설자가 참여자의 5배를 낸다). 추가 부담 상한은 두지 않았다. 개설자 부담금은 저장하지 않고 계산한다.
- **R**: `pricing.py`와 테스트 구현. 몫 1~20개 × 총액 2천여 가지 조합 전부에서 **합계 = 총액, 개설자 추가 부담 < 인원×10원**을 확인했다(테스트 통과). DB 변경 없음.
- **관련**: 기획서 5.3, 커밋 734ab66·e8ba262, `backend/app/pricing.py`

### TS-06. Supabase가 비밀번호 해시를 외부에 공개할 수 있었음

- **S**: Supabase는 `public` 스키마 테이블을 REST API(Data API)로 자동 공개한다. RLS가 꺼져 있으면 프로젝트의 공개 키만으로 `users.password_hash`까지 읽을 수 있다. 모든 접근이 FastAPI를 거친다는 설계 가정이 깨진다.
- **T**: 우회 경로를 기능 손실 없이 막는다.
- **A**: 첫 마이그레이션에서 세 테이블에 `ENABLE ROW LEVEL SECURITY`를 걸고 허용 정책을 하나도 두지 않았다. 백엔드는 테이블 소유자 계정으로 붙어 RLS의 영향을 받지 않는다.
- **R**: 적용 후 DB에서 직접 조회해 세 테이블의 RLS가 켜진 것을 확인했다(`alembic_version`만 꺼져 있고 번호 하나뿐이라 무해).
- **관련**: 기획서 5.7, `backend/alembic/versions/0001_initial_schema.py`

### TS-07. 마감 지난 글을 취소할 수 있었음

- **S**: 무산 기록이 늦으면 마감이 지난 글도 저장된 상태는 OPEN이라, 개설자가 이미 끝난 글을 취소할 수 있었다.
- **T**: 무산 기록 시점과 무관하게 취소 가능 여부를 정확히 판단한다.
- **A**: 취소의 조건부 UPDATE에 `deadline > now()`를 넣었다. 0행이면 재조회해 404/403/409로 가른다.
- **R**: 기획서 9.7과 QA("마감이 지났지만 아직 OPEN인 글을 취소 시도 → 409 NOT_OPEN")에 반영. 구현은 A-09 단계. **미확인**.
- **관련**: 기획서 9.7

### TS-08. Must 기능이 Should 기능에 의존

- **S**: 글 작성(Must)이 나눔의 "사진 필수"를 포함해 사진 업로드(Should) 없이는 완성되지 않았다. 일정도 나눔 탭이 업로드보다 먼저 잡혀 있었다.
- **T**: 핵심 기능만으로 데모가 성립하게 하고, 선택 기능이 핵심을 흔들지 않게 한다.
- **A**: Must는 같이사기만 다루고, 나눔 탭·사진 업로드·업로드 API를 **"나눔 묶음"**으로 묶어 끝까지 완성하거나 통째로 빼기로 했다. 일정은 업로드 → 나눔 탭 순으로 바꾸고 19.5h에 진행 여부를 판단한다. A-04는 지금 `type: SHARE`를 400으로 거절한다.
- **R**: A-04를 같이사기만으로 완성했고 거절 동작을 테스트했다(`{"type": "SHARE"}` → 400).
- **관련**: 기획서 4·13장, 커밋 0e10afa·e8ba262

### TS-09. 나눔 입력 폼과 DB 컬럼 불일치

- **S**: 나눔 폼에는 유통기한이 있는데 DB에는 그 컬럼이 없었다. 폼에 몫 수·가격 입력이 없는데 API는 "1몫·0원이 아니면 400"을 반환했다.
- **T**: 클라이언트가 보낸 값에 기대지 않고 나눔의 규칙이 항상 지켜지게 한다.
- **A**: 유통기한은 `deadline`에 저장하고, 나눔이면 서버가 1몫·0원으로 강제한다. DB에도 `CHECK(type<>'SHARE' OR (total_slots=1 AND total_price=0 AND image_url IS NOT NULL))`를 두었다.
- **R**: 마이그레이션에 제약이 들어갔고 DB 조회로 확인했다. 서버 쪽 강제는 나눔 묶음에서 구현.
- **관련**: 기획서 7.3, 7.5

### TS-10. 두 버전의 기획서가 서로 다른 결정을 담고 있었음

- **S**: 웹에서 고친 기획서와 로컬 기획서가 무산 저장 방식, 목록 범위, 에러 코드 이름, Must 범위를 서로 다르게 정하고 있었다.
- **T**: 하나의 기준 문서로 합치되 양쪽의 좋은 점을 잃지 않는다.
- **A**: 직접 리뷰를 거친 웹 버전의 결정을 기준으로 삼고, 로컬 버전의 구조(속성 표, 흐름도, API 예시)만 남겨 통합했다. 합치다가 드러난 빈틈(에러 코드 누락, 1몫 데모와 규칙 충돌 등)을 함께 고쳤다.
- **R**: 기획서 v3로 통합하고 변경 이력을 부록에 남겼다.
- **관련**: 기획서 부록

### TS-11. 성사 뒤 만날 방법이 없었음

- **S**: 참여자는 만남 장소를 볼 수 있지만 개설자는 누가 신청했는지 볼 API가 없었고, 연락 방법도 정의돼 있지 않았다.
- **T**: 거래가 실제로 끝나는 최소한의 정보를 제공하되 채팅은 만들지 않는다.
- **A**: 내 글 API(A-08)로 참여자 닉네임을 보여 주고, 만남 장소 메모에 장소·시간·연락 방법(오픈채팅 링크)을 함께 적게 했다. 메모는 개설자와 성사된 참여자에게만 응답한다.
- **R**: 기획서·DoD에 반영. 응답 스키마를 `ItemOut`(`pickup_note` 없음, 목록용)과 `ItemDetailOut`(작성자용)으로 나눠 구현했고 A-04가 후자를 쓴다. 목록(A-03)은 `pickup_note`가 응답 본문 어디에도 나오지 않는 것을 테스트했다(통과). 내 참여(A-06)에서의 공개 범위는 해당 단계에서 테스트한다. **일부 미확인**.
- **관련**: 기획서 3·5.2

### TS-12. 정의되지 않은 에러 코드와 정책 불일치

- **S**: 입력 오류, 이메일 중복, 로그인 실패, 인증 실패, 업로드 오류, 남의 글 취소의 코드가 없었다. 닉네임 정책은 기획서 한 곳만 "중복 불허"로 바뀌고 DB와 에러 코드에는 반영되지 않았다. 데모는 1몫 글을 쓰는데 규칙은 "2몫 이상"이었다.
- **T**: 문서와 코드가 같은 말을 하게 한다.
- **A**: 코드 8개를 추가하고 모든 에러를 `{code, message, field?}`로 통일했다. 닉네임은 "중복 허용"으로 통일했고 몫 하한은 1로 맞췄다. 에러 표를 코드(`ERRORS`)에 두고 **기획서 8장과 같은지 검사하는 테스트**를 만들었다.
- **R**: 테스트 통과. 기획서와 코드의 코드 목록·HTTP 상태·화면 문구 중 하나라도 어긋나면 실패한다.
- **관련**: `backend/app/errors.py`, `backend/tests/test_errors.py`, 커밋 82c8e3b

### TS-13. 확인할 수 없는 단정적 표현과 허술한 사진 주소 검증

- **S**: "집 위치를 알 수 없다", "월 0원 운영" 같은 표현은 사실과 다르거나 보장할 수 없다(좌표 격자는 정사각형이 아니고, 인구가 적은 곳은 위치가 좁혀지며, 무료 한도는 바뀐다). 사진 주소를 앞부분만 비교하면 다른 버킷이나 이상한 경로도 통과한다.
- **T**: 발표 질의에서 반박당할 표현을 없애고 입력 검증의 구멍을 막는다.
- **A**: "위험을 줄일 뿐 없애지는 못한다", "무료 플랜 범위 안에서 운영하는 것이 목표"로 고쳤다. 사진 주소는 `{SUPABASE_URL}/storage/v1/object/public/{버킷}/{UUID}.{jpg|png|webp}` 형식 **전체**를 정규식으로 검사한다.
- **R**: A-04에서 구현하고 다른 도메인, 다른 버킷, UUID가 아닌 이름, 허용되지 않은 확장자, 쿼리 문자열, 호스트를 덧붙인 주소 6가지가 모두 400으로 거절되는 것을 테스트했다(통과).
- **관련**: 기획서 5.2·5.3, `backend/app/item_schemas.py`

### TS-14. Supabase 직접 연결이 Render에서 붙지 않을 위험

- **S**: Supabase 무료 플랜의 직접 연결 주소는 IPv6 전용일 수 있어(대시보드에서도 "IPv6 네트워크가 아니면 Session pooler를 쓰라"고 안내한다), IPv6로 나가지 못하는 서버에서는 붙지 않을 수 있다. Render에서의 동작은 직접 확인하지 못했다. 로컬에서는 되다가 첫 배포에서 막힐 수 있다. 풀러 트랜잭션 모드(6543)는 prepared statement도 지원하지 않는다.
- **T**: 배포 환경의 연결 문제를 일정 후반이 아니라 처음에 해결한다.
- **A**: 풀러의 **세션 모드(5432)**를 쓰기로 했다(IPv4 프록시 제공, prepared statement 지원). 개발도 처음부터 Supabase에 붙였다.
- **R**: 개발 DB에 세션 풀러로 연결해 마이그레이션 적용과 `/health/db` 200을 확인했다. 배포 환경(Render)에서의 연결은 **미확인**.
- **관련**: 기획서 5.7

### TS-15. 마이그레이션의 CHECK 제약 이름이 두 번 붙음

- **S**: 모델에 이름 규칙(`ck_%(table_name)s_%(constraint_name)s`)을 두고 마이그레이션에도 `ck_items_type`처럼 최종 이름을 직접 적었더니, DB에 만들어질 이름이 `ck_items_ck_items_type`이 된다.
- **T**: DB에 적용하기 전에 제약 이름이 모델과 일치하게 한다.
- **A**: 적용 전에 `alembic upgrade head --sql`로 SQL만 뽑아 기획서와 비교하다가 발견했다. 마이그레이션의 이름을 `op.f()`로 감싸 "이미 최종 이름"이라고 표시했다.
- **R**: 수정 후 SQL에서 이름이 `ck_items_type` 등으로 나오는 것을 확인하고 적용했다. DB에서 제약 15개를 직접 조회해 기획서와 일치함을 확인했다.
- **관련**: `backend/alembic/versions/0001_initial_schema.py`, 커밋 8119275

### TS-16. `.env` 설정이 두 번 실패하고 비밀번호가 대화에 노출됨

- **S**: 비밀번호를 한 번에 붙여 넣으면 다음 명령이 비밀번호로 입력되므로 셸 명령을 두 단계로 나눠 안내했다. 사용자가 "완료"라고 한 뒤 `alembic upgrade head`가 `fe_sendauth: no password supplied`로 실패했고, `.env`의 `DATABASE_URL`에 비밀번호가 들어가지 않은 것이 직접 원인이었다. 그 이전 단계에서 왜 빠졌는지는 확인하지 못했다. 이어서 스크립트의 첫 질문(연결 문자열)에 비밀번호를 입력해 **대화에 노출**됐고, 한/영 키가 한글 상태라 입력도 깨졌다.
- **T**: 비밀번호를 대화에 남기지 않고 `.env`를 안전하고 확실하게 만든다.
- **A**: 비밀번호 입력, 특수문자 인코딩, 연결 테스트, `.env` 작성을 한 번에 하는 `scripts/setup_env.py`를 만들었다. 연결 문자열을 묻는 단계를 없애 비밀번호만 입력받고(`getpass`로 화면에 표시 안 함), 연결에 성공한 경우에만 파일을 쓴다. "영문 입력 상태 확인" 안내를 넣었고, 노출된 비밀번호는 재설정하도록 권고했다.
- **R**: 스크립트로 연결 성공, `alembic upgrade head` 적용, `/health/db` 200을 확인했다. 이후 저장소 키도 같은 방식(`setup_env.py storage`)으로 설정했다.
- **관련**: `backend/scripts/setup_env.py`, 커밋 8119275·07e7d7c

### TS-17. `.env`를 편집기로 저장했는데 반영되지 않음

- **S**: 사용자가 편집기에서 `.env`를 고쳤다고 했지만 파일의 마지막 저장 시각은 이전 그대로였고 `SUPABASE_URL`은 예시값, `SUPABASE_SERVICE_KEY`는 빈 값이었다. 저장소 접속 테스트가 DNS 오류(`nodename nor servname provided`)로 실패했다.
- **T**: 원인을 가리고, 다시 같은 문제가 생기지 않게 한다.
- **A**: 키 값을 출력하지 않고 항목별 "줄 수 / 값 있는 줄 수 / 예시값 줄 수"와 파일 저장 시각으로 진단했다. 저장되지 않은 편집 내용이 원인이라고 판단했다. 이후 `.env`는 편집기가 아니라 `setup_env.py storage`로만 고치기로 했고, 이 스크립트는 프로젝트 주소를 DB 주소에서 자동으로 만들고 Secret key 형식과 버킷 접속을 확인한 뒤에만 저장한다.
- **R**: 버킷 확인 결과가 기획과 일치했다(공개, 크기 제한 512,000바이트, jpeg·png·webp). Secret key로 Storage API가 200을 응답함도 이때 미리 확인했다.
- **관련**: 커밋 07e7d7c, `PROGRESS.md` 환경 메모

### TS-18. 도구 설치와 경로 문제

- **S**: 이 Mac에는 Homebrew, uv, Node가 없었고 시스템 Python은 3.9라 타입 문법과 라이브러리 지원 면에서 3.11 이상이 편했다. 설치 직후에도 기존 셸이 새 경로를 몰라 `node`, `uv`를 찾지 못했다.
- **T**: 관리자 권한 없이 필요한 도구를 설치하고, 셸 설정과 무관하게 동작하게 한다.

- **R**: uv 0.13, Python 3.12, Node 24 LTS, ruff 확인. 셸 설정을 읽지 않는 최소 환경(`env -i`)에서 훅이 파일을 정리하는 것을 확인했다.
- **관련**: `.claude/hooks/format.sh`

### TS-19. 포맷 훅이 세션 중에 적용되지 않음

- **S**: `.claude` 설정 폴더가 세션 시작 후에 생겨서 설정 감시 대상에 들어가지 않았고, 훅이 동작하는지 알 수 없었다.

### TS-20. uv 기본 구조와 템플릿 정리

- **S**: `uv init`이 `src/` 패키지 구조로 생성해 계획한 `app/` 구조와 달랐다. Vite 템플릿의 불필요한 파일을 `rm -rf`로 지우려 했더니 직접 만든 권한 규칙(`rm -rf` 차단)에 거부됐다.
- **T**: 계획한 구조로 정리하되 안전 규칙은 유지한다.
- **A**: `src/`와 빌드 설정을 지우고 `app/` 구조로 바꿨다. 규칙을 풀지 않고, 지울 파일을 `ls`로 확인한 뒤 강제 옵션 없이 하나씩 삭제했다.
- **R**: 프론트 빌드, prettier 검사, 린트 통과. 안전 규칙이 실제로 동작함을 확인했다.

### TS-21. 테스트용 가짜 환경 변수가 진짜 `.env`를 덮어쓸 위험

- **T**: `.env`가 없는 환경(가짜 값 필요)과 있는 환경(진짜 DB 사용)을 모두 지원한다.
- **A**: `tests/conftest.py`에서 `.env`가 **없을 때만** 가짜 값을 넣도록 했다.
- **R**: `.env`가 있을 때 테스트가 개발 Supabase DB에 실제로 쓰고 지우는 것을 확인했다(85개 통과, 종료 후 남은 테스트 계정 0개).
- **관련**: `backend/tests/conftest.py`

### TS-22. 검증 실패 시 영어 라이브러리 메시지가 화면에 나감

- **S**: 입력 오류를 `INVALID_INPUT`으로 통일하면서 pydantic의 메시지를 그대로 내보내면 이메일 형식 오류 같은 경우 영어 문장이 사용자 화면에 보인다.
- **T**: 직접 쓴 한국어 메시지만 노출하고 나머지는 입력 항목 이름만 알려 준다.
- **A**: 우리 검증 함수가 던진 오류는 메시지에 `Value error, ` 접두어가 붙는 점으로 구분해, 이 접두어가 있을 때만 메시지를 그대로 쓰고 나머지는 기본 문구와 `field`만 돌려주도록 했다. 처음에는 오류 종류(`value_error`)로 구분했는데, 이메일 형식 같은 라이브러리 검증 오류도 같은 종류로 분류될 수 있어 영어 문장이 새어 나갈 것으로 판단하고(실제로 새어 나가는 것을 재현해 보지는 않았다) 접두어 기준으로 바꿨다.
- **R**: 가입 입력 오류 10가지가 각자 올바른 `field`와 비어 있지 않은 한국어 문구를 반환하는 것을 테스트했다(통과). 이메일 형식 오류는 기본 문구로 응답함을 서버에서 확인했다.
- **관련**: `backend/app/errors.py`, 커밋 82c8e3b

### TS-23. 위도만 보낸 요청이 검증을 통과함

- **S**: 글 작성에서 `lat`은 보내고 `lng`을 생략한 요청이 `201`로 저장됐다. `lng`의 검증 함수에 "둘 중 하나만 있으면 오류" 규칙을 넣었는데, pydantic은 **생략된 필드에는 검증 함수를 실행하지 않기** 때문에 규칙이 한 번도 돌지 않았다. 테스트를 작성하다가 발견했다.
- **T**: 생략 여부가 의미 있는 필드에서 검증이 항상 돌게 한다.
- **A**: `lng`를 `Field(default=None, validate_default=True)`로 바꿔 기본값에도 검증이 돌게 했다. 같은 함정을 `PROGRESS.md`의 환경 메모에 적었다.
- **R**: 위도만 보낸 요청이 `400 INVALID_INPUT`(`field: lng`)으로 거절되는 것을 포함해 테스트 85개 통과.
- **관련**: `backend/app/item_schemas.py`, 커밋 e8ba262

### TS-27. 검색어의 `%`, `_` 가 와일드카드로 동작함

- **S**: 목록 검색은 `title ILIKE '%검색어%'`다. 사용자가 입력한 `%`는 "전부 일치", `_`는 "아무 한 글자"로 해석돼서, `%`를 검색하면 모든 글이 나오고 `a_b`를 검색하면 `axb`도 걸린다. 사용자 입력이 그대로 SQL 패턴이 되는 문제다(값은 바인딩되므로 SQL 주입은 아니다).
- **T**: 사용자가 입력한 문자를 그대로 찾는다.
- **A**: 검색어의 `\`, `%`, `_`를 먼저 이스케이프하고(`escape_like`) `ILIKE ... ESCAPE '\'`를 쓴다.
- **R**: `%`로 검색하면 `100% 오렌지` 한 건만, `a_b`로 검색하면 `a_b 세트`만(`axb 세트` 제외), `\`로 검색하면 백슬래시가 든 글만 나오는 것을 테스트했다. **이스케이프를 일부러 지우면 이 테스트가 실패하는 것도 확인**했다(변이 확인).
- **관련**: `backend/app/routers/items.py`, `backend/tests/test_items_list.py`

### TS-28. 반경 필터를 사각형 범위로만 하면 모서리가 포함됨

- **S**: 목록을 빠르게 줄이려고 DB에서 위도·경도의 사각형 범위로 먼저 거른다. 이 범위만으로 반경 필터를 대신하면 사각형 모서리(대각선)가 반경 안으로 들어온다. 위도 0.04°(약 4.4km) + 경도 0.04°(약 3.6km)인 글은 직선거리가 약 5.7km인데 5km 반경 안에 보인다.
- **T**: 정확한 반경 필터를 유지하면서 1,000건 기준 1초 이내(기획서 12장)를 지킨다.
- **A**: 사각형 범위는 후보를 줄이는 용도로만 쓰고, 실제 반경 필터와 정렬은 Haversine 거리로 파이썬에서 한다. 정렬은 거리, 마감, id 순으로 정해 같은 거리에서도 순서가 항상 같게 했다.
- **R**: 모서리 글이 걸러지는 테스트를 추가했고, 정확한 반경 필터를 일부러 지우면 반경 테스트 2개가 실패하는 것을 확인했다. 시드 1,000건을 넣고 측정하니 938건 응답에 **중앙값 약 85ms**(최대 115ms, 응답 327KB), 검색어를 넣으면 약 67ms였다.

### TS-30. 조건 하나를 지워도 동시성 테스트가 통과함

- **S**: A-05의 조건부 UPDATE에는 `status = 'OPEN'`과 `filled_slots < total_slots`가 함께 있다. 테스트가 정말 문제를 잡는지 보려고 구현을 일부러 망가뜨려 보던 중, `filled_slots < total_slots` 조건을 지워도 동시성 테스트 26개가 **전부 통과**했다. 테스트가 약한 것인지, 조건이 불필요한 것인지 알 수 없었다.
- **T**: 어느 쪽인지 가려서, 필요한 조건을 실수로 지우는 일을 막는다.
- **A**: 같은 UPDATE 안에서 마지막 몫이 차면 상태가 `CONFIRMED`로 바뀌므로, 뒤따르는 요청은 `status = 'OPEN'`에서 이미 걸러진다는 가설을 세웠다. 그렇다면 `filled_slots < total_slots`는 "상태와 몫이 어긋난 글(OPEN인데 이미 가득 참)"에만 의미가 있는 이중 안전장치이고, 그 경우는 동시성이 아니라 순차 테스트의 몫이다. 이 조건을 지운 채 순차 테스트를 돌려 가설을 확인했다.
- **R**: 가설이 맞았다. 순차 테스트 `test_full_items_are_409_sold_out[open_but_full]` **한 건만** 실패했다(DB의 CHECK 제약 위반으로 500). 두 조건을 모두 남기고, 각 조건을 지키는 테스트가 어느 것인지 알게 됐다: 원자성은 동시성 테스트(변이 시 20개 실패), 이중 안전장치는 `open_but_full`.
- **교훈**: 동시성 테스트는 "남은 몫만큼만 성공"을 검증하고, 개별 조건의 필요성은 상태 조합을 직접 만든 순차 테스트가 검증한다. 변이(일부러 망가뜨리기)로 확인하지 않았다면 이 구분을 몰랐을 것이다.
- **관련**: `backend/app/join.py`, `backend/tests/test_join.py`, `backend/tests/test_join_concurrency.py`
